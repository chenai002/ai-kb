# 08 · 工具调用：AI 怎么"操作"东西

> 模型本身只能"输出文字"。
> 那它怎么查天气、发邮件、下单？答案是：**它不操作，它只是"申请"要做，由程序去执行。**

---

## 一、核心认知：模型只会"说话"

先破除一个常见误解：

| 你以为 | 实际 |
| --- | --- |
| AI 自己去网上查了天气 | 程序去查了，把结果告诉了 AI |
| AI 打开了你的邮箱发信 | AI 说"请发这封信"，程序去发的 |
| AI 访问了数据库 | AI 写了条 SQL，程序执行了 |

**模型能做的只有一件事：输出文字。** 所有"操作"都发生在模型外面。

这就是**工具调用（Tool Calling / Function Calling）** 的全部秘密。

---

## 二、一次工具调用的完整过程

假设你问：**「明天杭州要带伞吗？」**

```
① 你提问
   "明天杭州要带伞吗？"

② 程序告诉模型：你有这些工具可用
   [
     { name: "get_weather",
       description: "查询指定城市某天的天气",
       parameters: { city: 字符串, date: 字符串 } }
   ]

③ 模型思考后，不直接回答，而是输出"我要调用工具"
   {
     "tool": "get_weather",
     "arguments": { "city": "杭州", "date": "2026-10-28" }
   }

④ 程序拿到这个请求，真的去调天气 API
   → 返回 { "weather": "小雨", "temp": "12-18℃" }

⑤ 程序把结果再发给模型
   "get_weather 返回：小雨，12-18℃"

⑥ 模型基于这个结果，生成最终回答
   "明天杭州小雨，气温 12-18℃，建议带伞。"
```

**关键点**：
- 第 ③ 步模型只是"输出了一段 JSON"，**它没有真的去调用任何东西**。
- 第 ④ 步是**你的程序**在做实际的调用。
- 所以：**工具调用 = 模型输出结构化指令 + 程序执行 + 把结果喂回模型**。

---

## 三、为什么这种方式这么有效

### 3.1 让模型"知道"能力边界

程序告诉模型「你有哪些工具」。模型就不会说"我无法查天气"，而是会说"我要调用 get_weather"。

### 3.2 用 Schema 约束输出

工具定义里有严格的参数说明：

```json
{
  "name": "get_weather",
  "description": "查询某城市某天的天气。城市用中文名，日期用 YYYY-MM-DD 格式。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市名，如'杭州'" },
      "date": { "type": "string", "format": "date" }
    },
    "required": ["city", "date"]
  }
}
```

模型必须输出符合这个结构的 JSON。**这比让模型自由发挥可靠得多。**

### 3.3 计算结果可以很精确

模型算数不可靠，但工具调用一个计算器就绝对准确。

> **一个重要的设计原则：让模型做"判断"，让工具做"精确计算"。**

## 四、工具长什么样（开发者视角）

### 4.1 一个工具的组成

```
名称：search_flights
用途说明：搜索指定日期从 A 城市到 B 城市的航班
参数：
  - from_city（必填）：出发城市
  - to_city（必填）：到达城市
  - date（必填）：日期
返回值：航班列表（航班号、时间、价格）
```

**说明写得好不好，直接决定模型会不会用对。**

### 4.2 实现方式（伪代码）

```python
# 1. 定义工具
tools = [{
    "type": "function",
    "function": {
        "name": "search_flights",
        "description": "搜索航班。仅在用户明确要订票时使用。",
        "parameters": { ... }
    }
}]

# 2. 第一次调用模型
response = model.chat(messages=[user_msg], tools=tools)

# 3. 检查模型是否要调用工具
if response.tool_calls:
    for call in response.tool_calls:
        # 4. 真正执行（这一段是你写的代码！）
        result = my_real_function(**call.arguments)

        # 5. 把结果放回对话
        messages.append(response.message)
        messages.append({"role": "tool", "content": result})

    # 6. 再调一次模型，让它基于结果回答
    final = model.chat(messages=messages, tools=tools)
```

**注意**：整个过程要调用模型**两次**（一次决定工具，一次生成答案）。

## 五、工具设计的黄金法则

### 5.1 一个工具只做一件事

```
✅ get_order_status(order_id)
✅ cancel_order(order_id, reason)
❌ do_whatever_with_order(action, params)   ← 模型会晕
```

### 5.2 描述要写给"什么都不懂的人"看

```
❌ "查询订单"                    （什么订单？怎么查？）
✅ "根据订单号查询订单状态（已支付/已发货/已签收），
    订单号格式为 20 位数字，通常以 ORD 开头。"
```

### 5.3 参数要少而明确

```
❌ { query: "查询语句" }         （模型自由发挥，不可控）
✅ { city: "...", date: "..." }  （结构清晰）
```

### 5.4 返回值要精简

```
❌ 返回完整的订单 JSON（3000 字）
✅ 返回关键字段：状态、金额、下单时间
```

**原因**：返回值会占用上下文，太长会挤掉其他信息，还费钱（见第 11 篇）。

### 5.5 错误信息要能帮助模型纠正

```
❌ "Error 500"
✅ "订单号 ORD123 不存在，请确认是否为 20 位数字，或检查是否输入有误"
```

模型看到具体的错误，才能自己修正。

## 六、几种特殊的"工具"

### 6.1 并行调用

模型可以一次请求多个工具：

```
用户：对比一下上海和北京的天气
模型：调用 get_weather(上海) 和 get_weather(北京)  ← 同时
程序：两个都执行，结果一起返回
```

**好处**：快。

### 6.2 MCP（Model Context Protocol）

一个**开放协议**，让"工具"可以标准化地提供给任何 AI 应用。

```
以前：每个 AI 应用都要为每个工具写一套适配
现在：工具实现一次 MCP Server，所有 AI 应用都能用
```

**打个比方**：MCP 就像"USB 接口标准"。工具做成"USB 设备"，任何"USB 主机"都能插。

**例子**：文件系统、数据库、GitHub、企业内部系统，都可以做成 MCP Server。

### 6.3 代码执行

有些 Agent 直接让模型"写代码，然后执行"：

```python
# 模型输出：
import pandas as pd
df = pd.read_csv("sales.csv")
print(df.groupby("region")["amount"].sum())
```

程序在**沙箱**里跑这段代码，把输出还给模型。

**风险**：代码是模型生成的，必须隔离执行（见 [12 · 安全](../04-limits/safety.md)）。

## 七、常见困惑

**Q：模型会自己"理解"工具返回的结果吗？**
会。结果作为文字回到上下文里，模型像读一段资料一样读它。

**Q：工具调用失败怎么办？**
把错误信息给模型，让它重试或换方案。所以错误信息要写清楚。

**Q：模型会不会乱调用工具？**
会。所以描述要明确"什么时候用、什么时候不要用"。

**Q：模型能不能一次调用 100 个工具？**
技术上可以，实际上会导致：
- 选择困难，准确率下降
- 定义本身占用大量上下文
**建议：同一场景下不超过 10–20 个工具。**

**Q：工具调用和 RAG 有什么区别？**
RAG 本质是"检索文档"这个特定工具。工具调用是更通用的：任何外部能力都可以做成工具。

**Q：需要自己写 MCP Server 吗？**
如果你想让 AI 操作你自己的系统，是的。但如果只是接入现成能力（如搜索、文件），社区有很多现成的。

## 八、一个完整的例子：行程助手

```
工具清单：
  search_flights(from, to, date)      搜索航班
  search_hotels(city, checkin, checkout) 搜索酒店
  get_weather(city, date)             查天气
  book_flight(flight_id, passenger)   订机票

用户：下周三去上海出差两天，帮我安排一下。

Agent 循环：
  ① 思考：需要先知道下周三的日期 → 2026-11-04
  ② 调 get_weather(上海, 2026-11-04) → 阴，15-20℃
  ③ 调 search_flights(杭州, 上海, 2026-11-04) → G12 08:00，¥73
  ④ 调 search_hotels(上海, 2026-11-04, 2026-11-05) → 3 家可选
  ⑤ 思考：信息够了，生成方案
  ⑥ 回答：
     "下周三上海阴天 15-20℃，建议带薄外套。
      推荐 G12 高铁（08:00-08:45，¥73）。
      酒店推荐：
        A 酒店 ¥398（近地铁）
        B 酒店 ¥520（含早餐）
      需要我帮你订吗？"
```

**注意最后一句**：涉及付钱的操作，要**停下来问人**。

## 九、用一句话解释给朋友听

> 「模型本身只会说话。工具调用就是：我们给它一张'能做什么'的清单，它想做什么就按格式'写申请'，我们的程序去执行，再把结果告诉它。所以真正动手的永远是程序，AI 只是决定'做什么'。」
