# 06 · RAG：让 AI 先查资料再回答

> RAG = Retrieval-Augmented Generation，检索增强生成。
> 名字很唬人，做的事很简单：**先查资料，再回答问题。**

---

## 一、先看一个真实的痛点

你做了个公司内部助手，员工问：

> 「我们的年假有多少天？」

AI 回答：

> 「一般企业年假是 5–15 天，具体看工龄…」

**它答错了。** 因为：
- 它不知道你们公司的制度（那是内部文档）
- 训练数据里没有这些内容
- 但它不会说"我不知道"，它会按"一般情况"编

### 1.1 三种解决思路

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| 改提示词 | 把制度直接写进提示词 | 文档太长、经常变，塞不下 |
| 微调 | 用这些文档训练模型 | 成本高、要重训、还会忘 |
| **RAG** | 需要时检索出相关片段，塞进提示词 | ✅ 成本低、可更新、可追溯 |

**RAG 就干一件事**：你问问题时，系统先去"文档库"里找到最相关的几段，然后把它们和你的问题一起发给模型。

```
没有 RAG：
  用户问题 ──────────────────▶ 模型 ──▶ 凭记忆回答（可能编）

有 RAG：
  用户问题 ──▶ 检索 ──▶ 找到相关文档片段
                              │
                              ▼
                   [文档片段 + 用户问题] ──▶ 模型 ──▶ 基于资料回答
```

## 二、RAG 的完整流程（小白版）

分成两个阶段：**建库**（提前做）和**查询**（每次提问）。

### 2.1 阶段一：建库（离线，一次或定期）

```
① 收集文档
   公司制度 PDF、FAQ、产品手册、Confluence 页面…

② 切分成块（Chunking）
   一本 100 页的文档 → 切成 200 个"小段落"
   为什么要切？因为模型不能一次吃下整本书

③ 每块转成向量（Embedding）
   把一段文字变成一串数字，比如 [0.12, -0.34, 0.88, ...]
   相似意思的文本，向量也相似

④ 存进向量数据库
   像给每段文字建索引
```

**关键概念：向量（Embedding）**

想象给每段文字打一组"特征分"：
```
"年假制度"        → [0.9, 0.1, 0.7, ...]
"带薪休假规定"    → [0.88, 0.12, 0.72, ...]   ← 很像！
"服务器故障排查"  → [0.1, 0.9, 0.2, ...]      ← 完全不同
```

计算机通过比较这两串数字的"距离"来判断语义相似度。

### 2.2 阶段二：查询（在线，每次提问）

```
① 用户提问：「年假怎么休？」

② 把问题也转成向量：[0.87, 0.15, 0.69, ...]

③ 在向量库里找最相似的几段（比如前 3 段）
   → 找到：《年假制度 v2.1》第二部分「年假规定」…

④ 把这 3 段和问题一起拼成提示词：
   「根据以下资料回答用户问题。
    <资料>
    （1）员工入职满 1 年享受 5 天年假…
    （2）年假需提前 3 个工作日申请…
    （3）年假可跨年…
    </资料>
    问题：年假怎么休？」

⑤ 模型基于资料回答，并可以标注来源
```

## 三、为什么 RAG 比微调更常用

| 维度 | RAG | 微调 |
| --- | --- | --- |
| 更新资料 | ✅ 改文档库即可，秒级 | ❌ 要重新训练 |
| 成本 | ✅ 低（向量化 + 存储） | ❌ 高（GPU + 标注） |
| 可追溯 | ✅ 能标出"答案来自哪段" | ❌ 说不清依据 |
| 权限控制 | ✅ 按用户过滤能检索的文档 | ❌ 训练进去就都有了 |
| 适合什么 | **事实型知识**（制度、手册、产品参数） | **风格、格式、特定任务能力** |

**结论**：查得到的事实用 RAG；"怎么说话、怎么做某类任务"用微调。

## 四、切分（Chunking）为什么重要

这是 RAG 里最容易翻车的地方。

### 4.1 切太大

```
一段 = 整章 5000 字
问题：检索出来一大段，但只有一句话有用
后果：浪费 token、干扰模型、答不准
```

### 4.2 切太小

```
一段 = 一句话
问题："年假规定" 只检索到半句「需提前 3 个工作日申请」
后果：缺少上下文，答案不完整
```

### 4.3 常见做法

| 做法 | 说明 |
| --- | --- |
| **按语义切** | 按段落、标题切，不硬切句子 |
| **固定长度 + 重叠** | 每块 500 字，相邻块重叠 50–100 字，避免关键句被切断 |
| **带元数据** | 每块标注"来自哪个文档、第几章、更新时间" |
| **小块检索 + 大块喂给模型** | 用小粒度找到，再把所在段落整体给模型 |

## 五、检索不准怎么办

这是 RAG 效果差的主要原因。常见改进：

| 问题 | 改进 |
| --- | --- |
| 关键词对不上 | 混合检索：向量检索 + 关键词检索（BM25）一起用 |
| 检索到的太泛 | 加**重排（Rerank）**：先用向量粗筛 50 条，再用模型精排取前 5 条 |
| 问题太口语 | **查询改写**：让模型先把"年假怎么休"改写成"员工年假天数与申请流程" |
| 文档有表格/图片 | 表格转成文字描述，图片用 OCR |
| 专业术语 | 建立同义词表 |

### 5.1 一个典型的"两段式检索"

```
① 向量检索：从 10 万段中粗筛 50 段（快）
② 重排模型：对这 50 段逐一打分（准，但慢）
③ 取前 5 段喂给大模型
```

**为什么两步**：纯向量检索快但不够准；全文精读准但太慢。两步兼顾。

### 5.2 Rerank（重排）到底是什么

**一句话**：把"检索"和"排序"拆成两份工作，让**便宜的模型做粗筛，贵的模型做精排。**

#### 为什么向量检索不够准

向量检索的做法是：把问题和文档片段各自变成一串数字（向量），比谁"离得近"。它有三个天然短板：

| 短板 | 例子 |
| --- | --- |
| **丢失细节** | 整段话被压成几百个数字，"必须是正式员工"这种限定条件容易被稀释掉 |
| **只比较整体相似度** | 一段讲"年假天数"、一段讲"年假申请"、一段讲"病假天数"——它们向量都很接近，但只有一个能回答问题 |
| **不理解问题的"意图"** | 问题是"年假能跨年吗"，而向量检索可能给你三段"讲年假"的段落，却都不是讲跨年的 |

**所以在 10 万段里，向量检索能保证"相关的都在前 50 名里"，但保证不了"最该排第几"。**

#### 重排模型做了什么

重排模型（Reranker）不是"再看一遍向量"，而是**把问题和候选段落放在一起，直接判断"这段有多能回答这个问题"**。

```
输入：  [问题] 年假能跨年结转吗？
        [段落] 员工年假原则上当年使用，确因工作需要未休完的，
               经部门负责人审批后可顺延至次年 3 月 31 日。

输出：  相关度分数 = 0.94
```

**关键差别**：

| | 向量检索 | 重排模型 |
| --- | --- | --- |
| 怎么算 | 分别把问题和文档变成向量，再比距离 | **两段文字一起读**，理解它们的对应关系 |
| 速度 | 极快（毫秒级，可检索百万条） | 慢（每对要算一次，通常只能算几十到几百条） |
| 精度 | 中等 | 高 |
| 角色 | **召回**：尽量不漏 | **排序**：把最对的挑出来 |

**打个比方**：

- 向量检索 = **图书管理员按书名/主题帮你搬来 50 本书**（快，但可能有凑数的）
- 重排 = **你自己坐下来，把这 50 本书的关键段落快速翻一遍，挑出真正回答问题的 5 本**（慢，但准）

#### 典型参数

```
召回 K = 50～200     向量检索先取这么多
重排后 top_n = 3～8   精排后只把这几段给大模型
```

**为什么不把所有段落都拿去重排**：重排要逐对计算，10 万段 × 每段一次模型前向，成本和时间都不可接受。

#### 重排模型长什么样

**不是大语言模型**，是专门训练的小模型（通常几亿参数，有的用 BERT 类结构）：

- 输入：问题 + 段落
- 输出：一个相关度分数

**因为小，所以快**；**因为专门为"判断相关性"训练过，所以准**。常见的中文/多语言重排模型在一些模型平台上可以直接调用，也可以本地部署。

#### 什么时候该加

| 情况 | 建议 |
| --- | --- |
| 文档几千段以上，回答经常"沾边但不准" | **强烈建议加** |
| 文档很少（几十段） | 可以不加，直接把全部给大模型 |
| 对延迟极敏感（要求 100ms 内） | 慎用，或只重排 top 10 |
| 问题里有强限定条件（"正式员工""跨年""税前"） | **建议加**，这正是向量检索的弱项 |

#### 常见误区

| 误区 | 事实 |
| --- | --- |
| Rerank 是"再检索一次" | 不是。检索已经完成，Rerank 只对候选重新排序 |
| 用了 Rerank 就不用管切分了 | 错。切分/切块仍然是基础，切得烂，重排也救不回来 |
| 重排能"补回"没召回的文档 | 不能。**召回阶段漏掉的，重排永远见不到**——所以召回 K 要够大 |
| 重排模型越大越好 | 不一定，要在精度和延迟之间取舍 |
| 向量库自带重排就够了 | 部分向量库支持，但效果通常不如专用重排模型 |

## 六、RAG 的常见坑

### 6.1 "它答得不对，是不是模型不行"

**多数时候不是模型的问题**，是检索没找到对的资料。

排查顺序：
1. 检索出来的 3 段里，有没有正确的那段？
2. 如果没有 → 检索问题（切分、向量化、索引）
3. 如果有，但回答错了 → 提示词或模型问题

### 6.2 资料本身是错的

RAG 只是"让模型读你给的资料"。**资料错，答案就错。**

### 6.3 资料冲突

三份文档说年假 5 天、10 天、15 天（不同年份的版本）。
**必须在入库前解决版本冲突**，或者把"更新时间"作为元数据让模型判断。

### 6.4 权限

销售部的文档不该被研发查到。
**必须在检索时按用户身份过滤**，而不是检索后再过滤（否则会泄露"存在这个文档"）。

### 6.5 它不看资料，靠记忆回答

```
❌ "请回答问题"
✅ "请只根据<资料>回答，资料里没有就说不知道"
```

提示词要强制"只用给定资料"。

## 七、什么时候不该用 RAG

| 场景 | 更好的选择 |
| --- | --- |
| 需要模型学会一种"说话风格" | 微调 |
| 需要模型学会一个"专业技能"（如医学术语） | 微调 |
| 数据量很小（少于几百字） | 直接写进提示词 |
| 需要实时计算、精确查询 | 用工具调用（见第 08 篇），比如查数据库 |

## 八、用一句话解释给朋友听

> 「RAG 就是给 AI 配了个'随身资料库'。你提问时，它先去资料库里找到最相关的几段，再对着文件回答。这样它不用靠记忆瞎编，还能告诉你答案出自哪一页。」

## 九、延伸：几个名词

| 名词 | 含义 |
| --- | --- |
| **Embedding（嵌入）** | 把文字变成向量的过程 |
| **向量数据库** | 专门存向量、做相似度检索的数据库 |
| **Chunk（块）** | 切分后的最小检索单元 |
| **Rerank（重排）** | 对检索结果二次排序：用专门的小模型逐段判断"能不能回答这个问题"，提高精度 |
| **Hybrid Search** | 向量 + 关键词混合检索 |
| **Graph RAG** | 用知识图谱组织结构，适合关系复杂的内容 |
